# Проект, облако и контрольные версии

Для сопровождения без отчета хранить актуальные требования/ТЗ, состояние ядра, журнал и нужные подтверждения. Папки иллюстраций, Word и сам report.md создавать по необходимости. Использовать фактические имена проекта; таблица ниже описывает возможные материалы, а не обязательный комплект пустых файлов.

## Структура работы

| Путь | Назначение |
| --- | --- |
| `project.md` или аналог | Требования/ТЗ, состав сдачи, состояние ядра и отчета, версии, проверки, решения, следующий шаг |
| ТЗ/карта требований по фактическому пути | Требуемый результат, ограничения, критерии и материалы объяснения; отдельно от фактов исполнения |
| `agent-logs/<run-id>.md` | Рабочий лог конкретного исполнителя; формат существующего AGENTS.md имеет приоритет |
| `report.md` | Выбранный рабочий текст; при продолжении сопоставить локальную и удаленную версии и записанный авторитет содержания |
| `sources/` | Методичка, задание, исходные материалы |
| `assets/cards/` | Учебные иллюстрации, схемы и карточки |
| `assets/code/` | Фрагменты реального исходного кода |
| `assets/screenshots/` | Скриншоты приложения от пользователя или из реального запуска |
| `assets/figure-index.md` | Файл, подпись, раздел, происхождение, коммит/расчет, легенда каждого рисунка |
| `checkpoints/<timestamp>-<label>/` | Снимок выбранного MD, assets, project.md, логов, output, конвертеров и manifest; без рекурсивного копирования checkpoints |
| `word-examples/` | DOCX-примеры и `catalog.md` с их статусом и областью применения |
| `output/` | Итоговый DOCX и явно запрошенные дополнительные форматы |

Не перестраивать существующий проект ради этих имен: записать фактические соответствия в project.md. Удаленные папки создавать по мере необходимости, а не десятками пустых каталогов.

Если отчет ведется, хранить в project.md выбранное имя MD (включая short/full), ID свежего DOCX, `content_authority`, `layout_authority` и `md_docx_diverged`. Если Word правился вручную, записать известные изменения и ссылку на конвертер/patch-скрипт. Для правки готового Word брать его актуальную версию, а не повторять первоначальный перенос из старого MD.

В кратком состоянии отмечать актуальный статус; прежние решения переносить в лог. Историческое «не принято» не должно выглядеть текущим после подтвержденной сдачи. Отдельный общий реестр оценок примеров не подменяет статус проектного файла.

## Синхронизация

Использовать подключенный коннектор выбранного пользователем сервиса. Для Google Drive предварительно прочитать его skill. Ссылки, ID и MIME-типы брать из ответов инструментов. Не менять размещение и общий доступ существующих материалов без задачи.

Обновлять рабочий MD по существующему ID. Рисунки синхронизировать с такими же относительными именами. `assets/code/example.png` переносим для скачанного дерева/редактора MD и конвертера; загрузка MD и картинки на Диск сама по себе не гарантирует показ картинки в веб-предпросмотре Drive. Не обещать непроверенную поддержку рендера. При необходимости дать доступ к самому рисунку по ссылке.

Перед записью перечитать файл, если пользователь мог менять его во время работы. При новой версии объединить непересекающиеся изменения. При содержательном конфликте показать конкретный спорный фрагмент. Использовать conditional write/version guard, если API поддерживает; при отсутствии не заявлять атомарной защиты, сверить версию непосредственно перед записью.

Снимки хранить отдельно от рабочего ID. Проверять результат каждой операции; успешная верхнеуровневая загрузка пакета не доказывает успех каждого файла. Не выдавать локальную копию за синхронизированную.

При запрошенной выдаче ZIP собрать необходимые файлы с переносимыми относительными путями, исключить кеши/разработческий мусор и проверить архив локально один раз. Передать его для распаковки пользователем; не загружать и не перечитывать отдельные файлы Drive только ради той же выдачи. Не заявлять установку пользователем. Реальные удаленные правки по-прежнему требуют проверки сохранения.

## Контрольная версия

На «сохрани текущую как контрольную, предыдущую оставь» копировать весь снимок с рисунками. Иначе замена картинки под тем же именем изменит визуальное содержание старого отчета.

Использовать UTC-метку в техническом имени; даты в общении показывать в часовом поясе пользователя. При совпадении имени добавлять уникальный суффикс. В manifest хранить хеш MD и каждого файла снимка, время, метку и исходный путь. Не включать хеш manifest внутрь него самого.

Различать `user-final` и `teacher-accepted`. Когда пользователь просит зафиксировать итог «пока не принятый преподавателем», использовать первый статус. Скрипт проверяет источник teacher-accepted по отдельному подтверждению; не генерировать подтверждение за пользователя. Для больших исходников хранить pinned URL/commit, явно отмечая, какие байты вошли в снимок, а какие материалы только связаны ссылкой.

Возвращаться к версии только по запросу, предварительно сохранив текущую незавершенную работу как draft. Восстанавливать текст вместе с его рисунками. Не удалять другие снимки.

После существенного результата основной работы или черновика и перед затратной либо прерываемой конвертацией/рендером сохранить соразмерное состояние и событие с указанием исполнителя, пока инструменты доступны. Включить фактические проверки/результаты, выбранные авторитетные MD/DOCX, состояние согласования, нерешенные вопросы и следующее действие; проверить запись. Если согласованное удаленное место недоступно, отметить ожидающую синхронизацию и допустимую локальную копию. Не создавать все папки отчета и не сохраняться перед каждой тривиальной операцией.

## Продолжение после паузы

Читать актуальное состояние и требования следующего этапа; текущий выбранный MD читать, если отчет уже ведется. Не перечитывать весь код после каждого «далее». Сохранять точные пути/коммит в заметках, проверять соответствующий код перед новым утверждением. Удаленный пользователем раздел не восстанавливать из старого снимка.

Перед перезаписью сопоставить выбранные локальные/удаленные версии и записанный авторитет содержания/оформления. Объединить непересекающиеся изменения; показать конкретные смысловые конфликты. Ни удаленное расположение, ни время изменения сами по себе не определяют авторитетную версию. Сохранить ручные правки DOCX, выбранные оформление/титул и известные расхождения MD/DOCX, включая ожидание согласования или одобрение конкретной редакции.

Файлы проверок в checks/ также включаются в снимок. Если доказательства лежат в другой папке, перечислить их отдельно и сохранить необходимые файлы; не утверждать, что произвольные пути попали в снимок автоматически. Аудит MD не декодирует изображения.

## Локальные команды

`report_workspace.py init <project> --mode accompany` создает минимальное состояние/папки журналов; необходимость отчета определяется заданием. `--mode report` (по умолчанию) создает материалы отчета, но не копирует Word-образец и не выбирает титул автоматически. Повторный init сохраняет существующие файлы, а не редактирует состояние.

`checkpoint <project> --mode accompany` не требует MD. Для отчетного снимка указать `--report <выбранное имя>`. Дополнительные ТЗ, пакеты и подтверждения за пределами стандартных папок включать повторяемым `--include <относительный путь>`; путь должен существовать внутри проекта и вне checkpoints. Так сохраняется реальное нестандартное расположение без переименования файлов.

Сверять `included_paths` и хеши manifest. Ссылки на внешние материалы не означают включения их байтов. Снимок состояния сопровождения не называть готовым отчетом. Не считать факт локального снимка облачной синхронизацией.
