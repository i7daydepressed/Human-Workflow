# Content and evidence

Map requirement → core result/answer → check → explanation section/material. Without an assigned final report, retain necessary state/explanation without an artificial table of contents. Do not create a formal section for every sentence of a guide when it duplicates the introduction. The introduction explains purpose, subject, and concrete outcome; the conclusion states what was achieved and supporting evidence. A “problem statement” does not remove the need for an introduction.

Present the overall process before models, fields, and individual methods. Use actual full method names and a pinned commit. Distinguish `Class.Method()` as a source locator from an instance call; that notation alone does not make a method static.

Link theory to practice with examples. Do not confuse structuring elements with filter weights or generalize one library's algorithm to all libraries. For library calculations, show preparation/call and verified behavior sources. Preserve selected units and channel, edge, anchor, and reflection conventions.

Keep development notes, hardware details, capture history, debug output, and launch tutorials out of the main report unless needed. Preserve reproducibility in sources, capture-notes, word-conversion, and logs. When shortening, remove repetition/history first while retaining requirements, results, key methods, errors, and evidence. Keep a separate short edition until the user selects it as primary.

Distinguish inspected source, actual build, calculated example, actual GUI run, user confirmation, and teacher acceptance. Retain known limits after acceptance; submission does not fix a defect.

Explain each illustration before it and interpret its concrete result after it. Give the example-specific conclusion before application. Avoid repeating the same introductory phrase. If requested, start operation paragraphs with a bold operation name; do not impose this everywhere.

Check complete sets/counts in knowledge tables against actual data. Source facts/ranges. An implementation plan does not prove current code. Prefer current files over memory while preserving user corrections.

Take theoretical questions, extra files, and demonstrations from the current assignment. Specifications/packets describe intent; artifact versions and checks establish implementation. After core changes identify affected claims/figures, update them or explicitly pin them to the older version.

For execution-result requests map clause → action/query → actual result → evidence → limit. A row count differs from the visible table portion. PREPARE does not establish EXECUTE. A separate calculation is not a target-app screenshot. Obtain/reproduce missing mandatory frames within available access and state gaps; do not hide them behind a calculated table.

Source external facts, rules, and ranges; distinguish authored formalization from expert assertions. Follow project preferences for language/punctuation/formatting; see user-profile.md.

## Present the selected content

For staged MD-to-Word work, show the actual current Markdown or an accessible link, identify its revision/hash and save pending approval in the existing state before conversion. Reuse approval covering the selected revision; record the source of explicit direct conversion or waiver instead of inventing approval. Material changes invalidate affected approval. For byte changes without a material content change, record reviewed equivalence and the revision relationship. Formatting-only changes to the authoritative DOCX preserve this content decision unless requirements or content change. See the [MD_APPROVAL contract](../workflow.md).
