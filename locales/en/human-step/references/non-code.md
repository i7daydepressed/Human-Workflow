# Steps for files, interfaces, and equipment

## Principle

Give a reproducible action, enough starting information, and a visible result. Complexity does not justify “do it as usual.” Avoid explaining obvious clicks when they do not help this recipient.

| Object | Specify exactly | Observe |
| --- | --- | --- |
| Text, table, configuration | File/revision, location, old/new blocks, values | Content, display, or behavior after applying |
| GUI application | Relevant version, screen, control name, value, order | Visible text/state or created file |
| Command/procedure | Working directory/context, literal command, parameters, start condition | Exit status, meaningful output, verified artifact |
| Device/connections | Confirmed model/revision, pin labels, power and suitable sourced diagram | Indicator, measurement, log, human confirmation |
| Data transfer | Exact source/destination, replacement conditions, retained data | Presence and content/hash, confirmed upload |

## Files and settings

Specify format and exact location: section, key, contextual line, cell range, or selected item. Separate literal commands/values from explanation. Mark placeholders; do not present an unfilled path, token, or address as executable.

Preserve syntax and unchanged fields. For file replacement, establish the current source and retained content. Update an existing cloud identity through the normal mechanism when the task requests an update rather than a copy. Local presence does not prove synchronization.

For a person, give steps in an available editor or explain where to run the command. Offer alternatives only when needed or requested.

## UI

Use real controls from inspected sources/observations. If version/appearance is unknown, state it and request only necessary clarification rather than inventing buttons. Prefer stable names to incidental coordinates.

Separate selecting, entering, applying, and saving from their effects. Specify exact values/units when material. Check the intended state change, not merely that a window closed.

While authoring, do not claim buttons were clicked or results observed. Give the human a check scenario; record their actual observation and its source after their response.

## Equipment and manual actions

Before concrete wiring, establish board/instrument model, revision, and a suitable source for labels. “ESP32” alone does not identify a particular board's pinout. List missing parameters precisely and pause only dependent steps; continue independent preparation.

For each connection, name both ends and confirmed conditions. For power and measurements, state the starting condition and observable result. Never invent voltages, pins, jumper positions, or successful discovery. Account for real constraints directly relevant to the operation.

Separate human actions from agent-accessible file preparation, settings, launches, and tool observations. A photo, user report, and telemetry provide different evidence; record provenance. Lack of physical tools does not prevent preparing reliable human instructions.

## Completion

Keep instruction preparation, actual execution, and checks separate. Return real states/files and confirmations for external actions. If an action did not occur, preserve a clear next step; a written instruction alone does not complete it.
