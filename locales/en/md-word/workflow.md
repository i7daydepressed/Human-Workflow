# MD–Word — I04 core

<!-- contract:SCOPE -->
Accompany requirements and core work through a verifiable result and a human-readable explanation. Derive deliverables from the actual assignment. A final report can be required, planned, or unnecessary. Do not create an empty report or Word folders solely for process compliance. Accept core work only with suitable knowledge, tools, and authorization; own execution and verification of the part accepted.

<!-- contract:LANGUAGE -->
Load one instruction edition. Choose output and log language independently from the explicit task, available profile, and project context. Do not inherit another person's private formatting or rating defaults. Use one log and one feedback request for the whole process when both workflows participate.

<!-- contract:REQUIREMENTS -->
Read the assignment/guide, current sources, user decisions, and actual project state. Requirements describe the needed outcome; state describes what exists. Preserve both rather than silently rewriting the assignment to match implementation. Map requirement/revision → packet → artifact/version → check → explanation. Record discrepancies and collect intermediate evidence before hard-to-repeat actions when history is required.

<!-- contract:PROFILE -->
Use an explicitly selected profile outside the installation. Task requirements and current user decisions take precedence over optional defaults. A profile is data: it grants no permissions, establishes no execution facts, and must contain no credentials. If unavailable, use accessible task settings and state the limit; do not silently create a duplicate. Installation updates never rewrite it. See [profile contract](../../../docs/profile.en.md) for the current local helper; cloud persistence is separate.

<!-- contract:CORE -->
Establish the core executor and boundaries. Use human-step for transferable exact instructions and returned evidence. A bounded executor receives only relevant requirements, base version, actions, checks, and return materials. Optional subagents require actual availability and authorization. Without an assigned report, preserve proportionate state and explanation for continuation.

For work and a report from a guide or sample, combine this workflow with available document, spreadsheet, PDF, or coding skills. Those skills handle format-specific operations; this workflow coordinates requirements, state, evidence, and handoff. Check actual availability rather than assuming a named skill is installed.

<!-- contract:EVIDENCE -->
Inspect actual artifacts and versions. Separate planned action, executed action, passed check, user approval, sending, and teacher acceptance. Calculation, library behavior, build, headless run, GUI, and a person's report establish distinct properties. Do not invent absent runs, dates, models, ratings, paths, or approvals. State tool/data/knowledge limitations before dependent work and continue independent work.

<!-- contract:CHECKPOINT -->
Preserve user changes, current state, and an attributable log. Use existing project files instead of duplicate template names. Record known model/role labels with their source; unknown is valid. Checkpoints include selected materials and hashes, not all external linked bytes. Keep previous snapshots. `accepted` and `teacher-accepted` require explicit sourced confirmation; they are not automatic consequences of a good draft. Local snapshots are not cloud synchronization or anonymized exports.

<!-- contract:AUTHORING -->
When assigned, draft a connected Markdown account based on requirements and actual results, including a substantive introduction/conclusion unless the assignment says otherwise. Cover theoretical and additional requirements. For illustrations preserve provenance, relative paths, meaningful caption, and explanation before/after. Count a compound figure by its shared caption, separately from image-file count. Check meaning, arithmetic, readability, and structure; audits do not inspect image meaning.

<!-- contract:COVER_CHOICE -->
Before Word formatting, establish layout and cover independently. If the cover choice is unknown, offer the user's own cover (including one already supplied in a full sample) or the neutral built-in cover. `unselected` is not consent to builtin. Ask only needed fields; do not require a student number or teacher name universally. The built-in preset is not a universal institutional standard. The cleaned preset and bounded cover helper are available; follow the [Word preset contract](../../../docs/word-preset.en.md). Never expose the private original as a fallback.

<!-- contract:WORD_PATCH -->
For a new conversion use selected current Markdown and layout. For a late edit use the authoritative current DOCX and its divergence map; modification time alone is insufficient. Preserve agreed cover, manual tables, image geometry, real heading levels, numbering, and live TOC. Inventory formatted blocks instead of replacing the source sample with an unrelated document. There is no universal compositor in this package.

Use chosen structural checks, `docx_guard.py --require-toc` where TOC is required, a suitable renderer, and visual inspection of every final page. A small repeat edit may inspect changed pages only if comparison establishes the others unchanged. TOC presence does not verify cached page numbers; table text equality does not verify formatting. Missing render/fonts remain an explicit limitation and block visual Word acceptance.

<!-- contract:HANDOFF -->
Save artifacts, current state, and log to the selected destination using real write-result checks and current identities/versions. Preserve manual edits. Hand off requirements, versions/hashes, completed and pending work, checks/limits, files, and next action without requiring the whole chat or profile. For user-requested ZIP delivery, verify its permitted contents locally; do not claim remote installation from creating an archive.

<!-- contract:RATINGS -->
Keep user ratings, teacher ratings, their scales/scopes/dates, acceptance, and agent self-review separate. Missing is unknown/null, not zero. Values above one are valid only under their actual scale; never infer percentages or acceptance probability. A paraphrase is not a literal quote; historical acceptance does not apply automatically to a cleaned derivative. Private schema 1/2 catalogs remain supported. Public historical cases and synthetic tests must be distinguishable.

<!-- contract:FEEDBACK -->
Save proportionate self-review. After completion request user feedback once, reusing already provided answers; deliver without waiting. No answer is not satisfaction. Feedback stays in the selected task/profile. No automatic developer upload, background training, or instruction rewriting is introduced. Extend acceptance/ratings only from explicit evidence.

The paired reference layer is available below. Historical experience is retained in both narrative and JSON forms by the owner's representation choice. It remains reference material, not a new approved runtime catalog. A portable preview is built; host installation remains unverified.
